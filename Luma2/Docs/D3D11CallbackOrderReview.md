# DX11 callback-order review

This review compares the native Luma 1.0 core in `Source/Core` with Luma 2.0 at `68931495`. It is a source review. The existing tests were inspected and were not run.

Most of the native call order already matches. Creation hooks still prepare arguments before the driver call and report successful objects afterward. State binds still record what the game set before notifying it. Copies and clears still give the game first refusal where an event exists. The differences worth reviewing are the ones that change what the next step can see, especially swapchain creation, mapped writes, and draw preparation.

## Callback sequences

| API path | Luma 1.0 order | Luma 2.0 order and assessment |
|---|---|---|
| **`D3D11CreateDevice` and device release** | Game pre-create → Core feature-level adjustment → native creation under the hook guard → hide the raised level from the game → discover vtables and wrap the device → initialize Core, then notify the game. On release, notify the game before Core teardown. | Same driver, proxy, and lifetime order. Pre-create now runs validation flag setup and SR negotiation. If Luma added the debug flag and creation fails, 2.0 retries without it. Game initialization runs after Core has its per-device state. [1.0 export](../../Source/Core/hooks/d3d11_hooks.cpp#L145) · [2.0 export](../Source/Core/Hooks/D3D11/D3D11Hooks.cpp#L154) · [2.0 lifetime handlers](../Source/Core/Handlers/Handlers.hpp#L24) |
| **`D3D11CreateDeviceAndSwapChain`** | Prepare device flags and levels → save the requested swapchain description → game edits it → Core applies swapchain policy → native call → report the device before the swapchain. | The detour still follows that outline, but the pre-create handler returns immediately when the creator is null. This skips both the game’s creation event and Core’s preparation. The null creator is expected here because the export creates the device and swapchain together. **This is the clearest ordering regression.** [1.0 combined export](../../Source/Core/hooks/d3d11_hooks.cpp#L203) · [2.0 combined export](../Source/Core/Hooks/D3D11/D3D11Hooks.cpp#L219) · [2.0 creator check](../Source/Core/Handlers/DXGI/DXGIHandlers.cpp#L161) |
| **Factory swapchain creation and resize** | Save the game’s request → let the game edit the call → apply Core policy → call DXGI → initialize swapchain state before the game’s completion callback. A failed resize restores the previous requested description. | Same broad order for the factory path. `on_create_swapchain` now receives a normalized description, and `on_init_swapchain` runs after successful resize setup. Rejected resizes restore the previous request and take a separate recovery path. This sequence is worth preserving, especially the distinction between the description reported to the game and the real buffers. [1.0 callbacks](../../Source/Core/core.hpp#L12194) · [2.0 resize detour](../Source/Core/Hooks/DXGI/DXGIHooks.cpp#L530) · [2.0 resize handlers](../Source/Core/Handlers/DXGI/DXGIHandlers.cpp#L310) |
| **Buffers, textures, views, and samplers** | Game pre-create can edit the descriptor → Core can alter creation arguments → native creation → attach lifetime tracking → Core initializes its state → game post-create. Sampler customization runs before the native call and sampler upgrade runs afterward. | The low-level wrapper is very similar. The principal intentional difference is where the texture upgrade happens. 2.0 creates the original first, then creates its mirror and mirrored views before the game’s init event. Buffer and texture-2D events retain the pre/post shape, and sampler descriptor edits still run before the native call. [1.0 resource callbacks](../../Source/Core/core.hpp#L12294) · [2.0 creation detours](../Source/Core/Hooks/D3D11/D3D11DeviceHooks.cpp#L31) · [2.0 resource handlers](../Source/Core/Handlers/D3D11/D3D11Handlers.cpp#L142) |
| **`Create*Shader` and `*SetShader`** | A game pre-create override can edit bytecode → Core sees the resulting bytecode → native creation → register the shader. At bind time, the game pre-bind override goes first, then Core selects and binds a replacement. | Core can prepare a compiled variant in the game’s creation hook before calling the driver → native creation → register the original and attach its variant → report the shader to the game. On bind, Core records the original shader and selects the variant before forwarding. The read-only creation event and per-device, per-hash variants are documented design changes. [1.0 shader callbacks](../../Source/Core/core.hpp#L12482) · [2.0 shader handlers](../Source/Core/Handlers/D3D11/D3D11Handlers.cpp#L249) · [Documented differences](Deviations.md#d3d11) |
| **State binds and `ClearState`** | Output-merger pre-callbacks run before Core substitutes views and calls the driver. Viewport and scissor callbacks run after the native call and Core tracking. `ClearState` calls the driver, resets Core’s trackers, then notifies the game. | The same ordering holds. Constant-buffer events run before Core records the game’s bindings. The main mismatch is inside the combined RTV/DSV/UAV bind, where 2.0 uses the RTV pointer to decide whether to process the DSV. [1.0 state callbacks](../../Source/Core/core.hpp#L12578) · [2.0 state callbacks](../Source/Core/Handlers/D3D11/D3D11Handlers.cpp#L289) |
| **`Map`, `Unmap`, and `UpdateSubresource`** | `Map`: native call → Core tracks a successful mapping → game callback. `Unmap`: game pre-callback → Core handles the write while the mapping is live → native unmap → game post-callback. `UpdateSubresource`: game gets first refusal. | `Map` and `UpdateSubresource` follow the same order. **`Unmap` is reversed at the front:** constant capture and the mirror upload run before `on_unmap`. A callback that changes mapped bytes can therefore leave Core with the earlier bytes, and returning `true` skips the native call after Core has already processed the write. [1.0 map and unmap](../../Source/Core/core.hpp#L12662) · [2.0 map and unmap](../Source/Core/Handlers/D3D11/D3D11Handlers.cpp#L394) |
| **Copy, resolve, and clear** | Game pre-callback can consume the call → Core traces and finds replacements → use a native copy where compatible, or a conversion path where supported. `CopyResource` also has a game override after mirror selection. | Common ordering is close. An exposed game event runs first → trace records the game’s request → Core redirects or forwards it. The later `OverrideCopyResource` point has no equivalent in this path. 2.0 also has narrower conversion coverage for partial region copies and cross-format MSAA resolves. Those are behavior differences beyond ordering. [1.0 copy path](../../Source/Core/core.hpp#L8638) · [2.0 callbacks](../Source/Core/Handlers/D3D11/D3D11Handlers.cpp#L466) · [2.0 mirror copy and resolve](../Source/Core/Resources/D3D11/D3D11Mirrors.cpp#L1546) |
| **Draw and dispatch** | Native game `PreDraw*` can consume the call before Core. Core prepares the pass → runs its custom-pipeline callback → runs the matching shader callback or generic game callback → issues or forwards the draw and restores temporary state as needed. | Core prepares mirror/scale state → binds patch prerequisites → runs the variant event → runs a shader-specific or generic event → binds remaining resources for an unhandled draw → restores its constant-buffer slots if configured. The **variant-first, specific-or-generic** sequence carries over. The early native veto, hash matching, and slot restoration differ. Also, `FinishDrawOrDispatch` can run before the original draw on the ordinary passthrough path, despite its name. That deserves clarification before any reorder. [1.0 draw callbacks](../../Source/Core/core.hpp#L6422) · [2.0 draw sequence](../Source/Core/Handlers/D3D11/D3D11Handlers.cpp#L579) · [Native fallback](../Source/Core/Hooks/D3D11/D3D11ContextHooks.cpp#L334) |
| **Deferred contexts and command lists** | Create context natively → track and observe it → notify the game. Finish natively → transfer list bookkeeping and reset the context if requested → notify the game. Execute gives the game first refusal → updates Core bookkeeping → calls the driver. | The same relative order. 2.0 uses context caches and separate trace bookkeeping. It invalidates cached uploads at the command-list boundaries and forgets bound state when `restore` is false. This is a close port. [1.0 list bookkeeping](../../Source/Core/core.hpp#L5105) · [2.0 deferred-context creation](../Source/Core/Hooks/D3D11/D3D11DeviceHooks.cpp#L346) · [2.0 finish and execute](../Source/Core/Handlers/D3D11/D3D11Handlers.cpp#L646) |
| **`Present` and `Present1`** | Core composes the frame before the game’s `OnPresent`. The overlay and native present follow. The proxy remembers a `WAS_STILL_DRAWING` result and skips Luma’s frame work on a retry. | The normal 2.0 order is game `on_present` → per-device frame work → display update and composition → overlay → native present → advance swapchain state on success. The callback-before-composition placement is explicit in 2.0 and lets the callback contribute to the frame being composed. The missing retry guard is a separate difference. [1.0 game present callback](../../Source/Core/core.hpp#L5591) · [1.0 proxy retry](../../Source/Core/hooks/dxgi_hooks.cpp#L602) · [2.0 frame order](../Source/Core/Handlers/DXGI/DXGIHandlers.cpp#L469) · [2.0 proxy present](../Source/Core/Hooks/DXGI/DXGIHooks.cpp#L732) |

## Decisions to review

1. **Restore the combined creation path first.** The change at `68931495` made unknown creators resolve to no API, which is sensible for a generic DXGI factory call. The combined export already knows it is D3D11. Its pre-create path should carry that knowledge so descriptor edits and swapchain policy run before native creation. The post-create callback can still fire today because it receives the device afterward. The existing test checks that notification, so it can pass while the pre-create work is skipped. [Creator dispatch](../Source/Core/Handlers/DXGI/DXGIHandlers.cpp#L161) · [Swapchain state creation](../Source/Core/Swapchain/DXGI/DXGISwapchain.cpp#L539) · [Existing combined-export test](../Source/Tests/DevicesTests.cpp#L566)
2. **Restore depth-only binding parity.** With zero RTVs and a null RTV array, the call can still supply a DSV. 1.0 handles that DSV independently. 2.0 skips its mirror substitution because `views` is null. The `D3D11_KEEP_RENDER_TARGETS_AND_DEPTH_STENCIL` sentinel is the condition that preserves the existing DSV. Separately, the combined 2.0 bind swaps pixel UAV pointers without using the overload that records pixel UAV slots for chain tracking. That second difference needs verification against a chain-dependent pass. [1.0 DSV handling](../../Source/Core/core.hpp#L4682) · [2.0 combined bind](../Source/Core/Handlers/D3D11/D3D11Handlers.cpp#L326) · [Microsoft output-merger contract](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11devicecontext-omsetrendertargetsandunorderedaccessviews)
3. **Resolve the `Unmap` contract before moving it.** The public 2.0 event comment and 1.0 both put the game callback before redirection. If a callback completes `Unmap` itself, Core cannot safely read the mapping afterward. The behavior to agree on is what Core captures when the callback lets the call proceed and what Core discards when the callback takes ownership. [2.0 public event contract](../Source/Core/Game/GameEvents.hpp#L117) · [Native unmap detour](../Source/Core/Hooks/D3D11/D3D11ContextHooks.cpp#L237)
4. **Review nonblocking retries independently of frame composition order.** 2.0 can repeat game callback, composition, and overlay work after `DXGI_ERROR_WAS_STILL_DRAWING`. Restoring the retry behavior is a separate decision from where `on_present` belongs within a normal frame. The latter has a documented 2.0 rationale. [2.0 composition order](../Source/Core/Handlers/DXGI/DXGIHandlers.cpp#L469) · [Microsoft present flags](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/dxgi-present)

## Legacy comments worth restoring

- **Swapchain creation and resize.** Explain why the combined export suppresses nested factory handling, why it reports the device first, and why zero buffer count or `DXGI_FORMAT_UNKNOWN` resolves against the game’s saved description. Keep the dgVoodoo example concrete: a changed refresh rate in `GetDesc` could trigger swapchain recreation every frame. At the resize call, explain why Luma goes through the proxy so overlay hooks can release their back-buffer references. [1.0 DXGI rationale](../../Source/Core/hooks/dxgi_hooks.cpp#L91) · [2.0 proxy resize](../Source/Core/Swapchain/DXGI/DXGISwapchain.cpp#L374)
- **Format-sensitive copies and resolves.** Document that a native copy can reinterpret bits within a compatible format family, while a shader blit can convert values or scale pixels. Explain why the conversion path resolves MSAA first and why it uses non-sRGB views for a raw-value blit. Keep the resolve format rules beside the native resolve call, where they can prevent treating copy and resolve compatibility as interchangeable. [1.0 format rationale](../../Source/Core/core.hpp#L8415) · [2.0 converting copy](../Source/Core/Resources/D3D11/D3D11Mirrors.cpp#L589) · [Microsoft copy rules](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11devicecontext-copyresource) · [Microsoft resolve rules](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11devicecontext-resolvesubresource)
- **Feature levels, bind sentinels, and pointer lifetimes.** Keep the reason a null feature-level list needs explicit handling to try 11.1, and why the detour preserves the game-visible level. At the combined bind, explain the difference between zero views and `D3D11_KEEP_*`. At `Unmap`, say exactly which steps must finish while `pData` is valid. These are comments that constrain future changes to call order.
